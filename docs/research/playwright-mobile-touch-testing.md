# Playwright Mobile/Touch Emulation for WebGL Canvas Testing

Research for [Mark-DSouza/jive-wiki issue #24](https://github.com/Mark-DSouza/jive-wiki/issues/24), part of the [Mobile compatibility — planning map (#18)](https://github.com/Mark-DSouza/jive-wiki/issues/18). Builds on the prior research at [`docs/research/testing-webgl-threejs-playwright.md`](https://github.com/Mark-DSouza/jive-wiki/blob/research/testing-webgl-threejs-playwright/docs/research/testing-webgl-threejs-playwright.md) (issue #6), which established that jive-wiki's desktop Playwright suite avoids pixel/screenshot testing of the WebGL canvas and instead does real pointer interaction: `e2e/graph-detail-panel.spec.ts` computes each node's live screen position via `graph.graph2ScreenCoords()` (an exposed `window.__jiveGraph` instance) and then does `page.mouse.move()` → wait a frame → `page.mouse.down()`/`up()` at that point, because the underlying render library (`three-render-objects`, which `3d-force-graph` wraps) raycasts against a hover target that's refreshed once per render frame on `pointermove` and rechecked on `pointerup`. The question here is whether the same "real interaction at a computed screen coordinate" strategy carries over to touch.

## Question 1: Device profiles for phone-portrait testing

Playwright ships a registry of device descriptors, spread into a project's `use` block via `devices['<name>']` — [Playwright docs: Emulation](https://playwright.dev/docs/emulation). The canonical source of these values is [`packages/isomorphic/deviceDescriptorsSource.json`](https://github.com/microsoft/playwright/blob/main/packages/isomorphic/deviceDescriptorsSource.json) in the `microsoft/playwright` repo — fetched directly for this research. Relevant phone-portrait entries (~360–430px wide):

| Device | `viewport` | `deviceScaleFactor` | `isMobile` | `hasTouch` | `defaultBrowserType` |
|---|---|---|---|---|---|
| `iPhone SE` | 320×568 | 2 | `true` | `true` | `webkit` |
| `iPhone 13` | 390×664 | 3 | `true` | `true` | `webkit` |
| `iPhone 14` | 390×664 | 3 | `true` | `true` | `webkit` |
| `iPhone 15` | 393×659 | 3 | `true` | `true` | `webkit` |
| `Pixel 5` | 393×727 | 2.75 | `true` | `true` | `chromium` |
| `Pixel 7` | 412×839 | 2.625 | `true` | `true` | `chromium` |
| `Pixel 8` | 412×839 | 2.625 | `true` | `true` | `chromium` |

All of these set `isMobile: true` and `hasTouch: true` unconditionally — every phone-portrait entry in the registry does, since `isMobile`/`hasTouch` are definitional to being a phone profile. `isMobile` also flips on the "mobile" viewport meta behavior (affects things like `window.innerWidth` interaction with `<meta name="viewport">`) and is only honored by Chromium-based browsers per Playwright's `Browser.newContext` docs — WebKit and Firefox ignore `isMobile` (it's a CDP-only emulation feature) but still honor `hasTouch` and `viewport`, so touch dispatch works cross-browser even though the `isMobile` viewport-meta behavior doesn't.

The important split: **iPhone profiles default to WebKit, Pixel profiles default to Chromium.** jive-wiki's CI (`.github/workflows/ci.yml`) currently only installs the Chromium browser binary (`npx playwright install --with-deps chromium`), and `playwright.config.ts` has a single `chromium` project. Adding an iPhone-based project would require also installing WebKit in CI (`npx playwright install --with-deps webkit` or `--with-deps` for all); a Pixel-based project needs no new browser install.

Configuring a second project alongside the existing desktop one, per the docs' own example:

```ts
import { defineConfig, devices } from '@playwright/test'

export default defineConfig({
  // ...existing config...
  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
    {
      name: 'mobile-chromium',
      use: { ...devices['Pixel 5'] },
    },
  ],
})
```

— [Playwright docs: Emulation](https://playwright.dev/docs/emulation) shows this exact `projects` shape (desktop Chrome + `devices['iPhone 13']` as "Mobile Safari" in their example; substituting `Pixel 5` keeps the whole suite on one browser engine already installed in CI). Each project runs the full `testDir` against its own `use` config, so no test code changes are needed for basic viewport/touch coverage — only new spec files (or a `test.describe` gated by project name) that specifically want mobile-only assertions (no horizontal overflow at ~375px, tap-outside-to-close, etc.).

Sources: [Playwright docs — Emulation](https://playwright.dev/docs/emulation), [`deviceDescriptorsSource.json` (raw, microsoft/playwright `main`)](https://raw.githubusercontent.com/microsoft/playwright/main/packages/isomorphic/deviceDescriptorsSource.json), jive-wiki's own `playwright.config.ts` and `.github/workflows/ci.yml`.

## Question 2: Does a real touch tap hit the canvas the same way as the real mouse click?

**Short answer: for a single tap, yes — with one required config flag and one API-choice caveat; jive-wiki's click-handling code already listens on the event type touch produces.**

**`3d-force-graph`'s interaction layer is Pointer-Events-based, not mouse-events-based.** Fetching `three-render-objects`' source (the library `3d-force-graph` wraps for the render/interaction loop) directly confirms the container's listeners are `pointermove`, `pointerdown`, and `pointerup` (click is resolved on `pointerup` against a hover target computed via raycasting on the last `pointermove`) — [`three-render-objects.js` (raw, `vasturiano/three-render-objects` `master`)](https://raw.githubusercontent.com/vasturiano/three-render-objects/master/src/three-render-objects.js). This matters because the Pointer Events spec is exactly the abstraction that unifies mouse and touch input at the browser level — a `pointerdown`/`pointerup` pair fires with `pointerType: 'mouse'` for a mouse click and `pointerType: 'touch'` for a touch tap, and `3d-force-graph`'s click handler doesn't distinguish between them. So architecturally, touch input should reach the same code path the existing desktop tests already exercise.

**Playwright's touch API is `page.touchscreen.tap(x, y)` (or the higher-level `locator.tap()`), and it requires `hasTouch: true` on the browser context** — confirmed directly in Playwright's own docs source: `touchscreen.tap()` "Dispatches a touchstart and touchend event with a single touch at the position (x,y)" and "will throw if the hasTouch option of the browser context is false" — [`class-touchscreen.md`](https://playwright.dev/docs/api/class-touchscreen). `locator.tap()` is documented as internally using `page.touchscreen` to tap the element's center (or a given `position`) — [`class-locator.md`, `Locator.tap`, raw](https://raw.githubusercontent.com/microsoft/playwright/main/docs/src/api/class-locator.md) (search `## async method: Locator.tap`). Because jive-wiki's existing `clickNode()` helper computes an arbitrary point on the canvas (not a DOM element with its own bounding box — the canvas has no per-node DOM structure), the direct analogue of the existing `page.mouse.move/down/up` pattern is `page.touchscreen.tap(x, y)` at the same `graph2ScreenCoords()`-derived point, not `locator.tap()`.

All three Playwright engines (Chromium, WebKit, Firefox) implement this touchscreen tap at the browser-automation-protocol level, confirmed by reading `playwright-core`'s server source directly:
- **Chromium**: `RawTouchscreenImpl.tap()` sends `Input.dispatchTouchEvent` with `type: 'touchStart'` then `type: 'touchEnd'` over CDP — [`crInput.ts` (raw)](https://raw.githubusercontent.com/microsoft/playwright/main/packages/playwright-core/src/server/chromium/crInput.ts).
- **WebKit**: `RawTouchscreenImpl.tap()` sends its own protocol message, `Input.dispatchTapEvent` — a *different* WebKit Inspector Protocol call, not a CDP passthrough — [`wkInput.ts` (raw)](https://raw.githubusercontent.com/microsoft/playwright/main/packages/playwright-core/src/server/webkit/wkInput.ts).
- **Firefox** has its own `RawTouchscreenImpl` too (`ffInput.ts`), not inspected in depth here since jive-wiki doesn't currently target Firefox.

Because these are dispatched through each browser's own low-level input/automation protocol (not synthetic JS `dispatchEvent()` calls from within the page), the browser engine processes them through its real input pipeline and — per each engine's own touch-to-pointer-event translation, the same one real hardware touch input goes through — generates trusted `pointerdown`/`pointerup` events with `pointerType: 'touch'`, in addition to the legacy `touchstart`/`touchend`. This is standard browser-engine behavior for any UA that supports both Touch Events and Pointer Events, not a Playwright-specific guarantee, but it's the mechanism that makes `touchscreen.tap()` a *real* touch simulation rather than a synthetic-event shim.

**Playwright's own maintainers confirm the design intent directly**, closing a feature request for broader touch-event emulation with: *"At this time, we don't plan to add native support for touch event emulation in Playwright. Clicks and other mouse actions already generate the corresponding `PointerEvents`, which is the modern and widely supported standard."* — [microsoft/playwright#2903](https://github.com/microsoft/playwright/issues/2903) (closed, maintainer comment). This is direct confirmation from the source that both `page.mouse` actions and `page.touchscreen.tap()` are expected to be consumed via Pointer Events by app code, which is exactly `3d-force-graph`'s model.

**Known gotchas:**
1. **`hasTouch: true` is mandatory** — omitting it (e.g. reusing a desktop `use` block without spreading a `devices[...]` entry) throws synchronously rather than silently no-opping, per the `Touchscreen` source above (`throw new Error('hasTouch must be enabled...')`). Using one of the `devices[...]` profiles from Question 1 sets this automatically.
2. **`touchscreen.tap()` only synthesizes `touchstart` + `touchend` — no `touchmove` in between**, unlike the existing `realClick()` helper's explicit `page.mouse.move()` → wait-a-frame → `down()`/`up()` sequence, which exists specifically to give `three-render-objects`' hover-target raycast a chance to run on a `pointermove` before the click is evaluated (see the comment in `e2e/graph-detail-panel.spec.ts` above `realClick`). A single `touchscreen.tap(x, y)` at a point that was never "hovered" via `pointermove` risks the same stale-hover-target race the existing comment warns about for mouse — worth verifying empirically whether a bare `tap()` reliably lands on the node, or whether the equivalent of the pre-press settle (waiting a rendered frame after the implicit `pointerdown`) is still needed. Playwright doesn't expose a separate "touch move-then-tap" primitive; the workaround is the same legacy-touch-event `dispatchEvent()` path covered in Question 3.
3. **WebKit vs Chromium use genuinely different protocol calls** (`Input.dispatchTouchEvent` vs `Input.dispatchTapEvent`), so behavioral parity between the two engines for edge cases (timing between synthetic `touchstart`/`touchend`, whether a `pointercancel` can occur) is not something Playwright's cross-browser abstraction guarantees identically — it's two independent implementations converging on "look like a tap," not one shared code path.
4. A WebKit-specific report of `page.mouse` actions not producing effects on a custom pointer-event-driven canvas exists ([microsoft/playwright#38370](https://github.com/microsoft/playwright/issues/38370)) but was **closed as unreproducible** by a Playwright maintainer, who stated plainly *"This is surprising, as we expect this to work"* — i.e. not a confirmed engine limitation, just an open flag that canvas + WebKit + pointer events is a combination worth verifying directly against jive-wiki's own build rather than assuming from other projects' reports.

Sources: [`three-render-objects.js` (raw)](https://raw.githubusercontent.com/vasturiano/three-render-objects/master/src/three-render-objects.js), [Playwright docs — `Touchscreen`](https://playwright.dev/docs/api/class-touchscreen), [`class-locator.md` (raw, `Locator.tap`)](https://raw.githubusercontent.com/microsoft/playwright/main/docs/src/api/class-locator.md), [`class-page.md` (raw, `Page.tap` — discouraged in favor of `Locator.tap`)](https://raw.githubusercontent.com/microsoft/playwright/main/docs/src/api/class-page.md), [`crInput.ts` (raw)](https://raw.githubusercontent.com/microsoft/playwright/main/packages/playwright-core/src/server/chromium/crInput.ts), [`wkInput.ts` (raw)](https://raw.githubusercontent.com/microsoft/playwright/main/packages/playwright-core/src/server/webkit/wkInput.ts), [`input.ts` (raw, shared `Touchscreen`/`hasTouch` guard)](https://raw.githubusercontent.com/microsoft/playwright/main/packages/playwright-core/src/server/input.ts), [microsoft/playwright#2903](https://github.com/microsoft/playwright/issues/2903), [microsoft/playwright#38370](https://github.com/microsoft/playwright/issues/38370).

## Question 3: Multi-touch (pinch/rotate) gestures against the camera controls

**jive-wiki's camera controls are, specifically, `TrackballControls` from three.js** (the default `controlType` in `three-render-objects` when unset — confirmed both by `three-render-objects.js`'s own default parameter, `controlType = 'trackball'`, and by there being no `controlType` override anywhere in jive-wiki's `src/`). Fetching the actual controls implementation confirms it is itself Pointer-Events-based and does its own multi-touch bookkeeping in application code, not via legacy `TouchEvent`s: `TrackballControls` listens for `pointerdown`/`pointermove`/`pointerup`, keeps every active pointer in a `this._pointers` array keyed by `pointerId`, and branches on `this._pointers.length` — one active pointer rotates, two active pointers compute `_touchZoomDistanceStart/End` (pinch distance) between the two `pointerId`s for zoom, and checks `event.pointerType === 'touch'` at several points — [`TrackballControls.js` (raw, `mrdoob/three.js` `dev`)](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/controls/TrackballControls.js). So a faithful pinch/rotate simulation needs **two simultaneous, independently-tracked pointers with distinct `pointerId`s and `pointerType: 'touch'`**, not just two touch points bundled into one legacy `TouchEvent.touches` list.

**Playwright's public API has no multi-touch primitive at all** — `touchscreen.tap()` is single-point, single-touch only, and this is a long-standing, still-open gap, not an oversight specific to old versions:
- The original feature request for pinch/swipe support was closed by maintainers with the same "we don't plan to add native touch emulation" answer as Question 2 — [microsoft/playwright#2903](https://github.com/microsoft/playwright/issues/2903).
- A follow-up request specifically for touch drag and low-level touch primitives (`touchscreen.down()/move()/up()`, analogous to the existing `mouse.down()/move()/up()`) is **still open as of January 2026** — [microsoft/playwright#39043](https://github.com/microsoft/playwright/issues/39043) ("Currently, Playwright lacks native support for touch drag operations and low-level touch primitives... there's no built-in way to Perform drag operations on touch devices... Simulate complex multi-touch gestures").
- A dedicated CDP-based pinch-zoom API exists at the protocol level (`Input.synthesizePinchGesture`) but Playwright doesn't expose it, and independent reports describe it as "marked experimental and proved unreliable in CI/CD pipelines" when used directly — [Martin Grandrath, "Testing touch gestures with Playwright" (2024)](https://www.martin-grandrath.de/blog/2024-05-01_testing-touch-gestures-with-playwright.html).

**What Playwright does document as the fallback is manual event dispatch via `locator.dispatchEvent()`**, and its own guide gives a worked pinch example: two `Touch` points with distinct `identifier`s, moved closer/further apart across several `touchmove` dispatches — [Playwright docs: Touch events (legacy)](https://playwright.dev/docs/touch-events). Two things undercut this for jive-wiki specifically:
1. **The guide's own caveat**: *"`locator.dispatchEvent()` does not set `Event.isTrusted` property."* Untrusted synthetic events are exactly the kind of input some pointer-capture / gesture-recognition code paths distinguish or refuse — and TrackballControls calls `setPointerCapture` in its pointerdown handler, a browser API whose interaction with untrusted synthetic `PointerEvent`s (as opposed to `TouchEvent`s) is not guaranteed the same as with real input.
2. **It dispatches `TouchEvent`s, but TrackballControls listens for `PointerEvent`s.** `page.dispatchEvent()`/`locator.dispatchEvent()` construct and fire the JS event object named in the call (`new TouchEvent('touchstart', ...)`) directly into the DOM; they don't run it through the browser's native touch-to-pointer-event synthesis pipeline the way a CDP/protocol-level `Input.dispatchTouchEvent` does. Since TrackballControls' pinch/rotate logic is driven entirely by `pointerdown`/`pointermove`/`pointerup` with `pointerId` bookkeeping (not `touchstart`/`touchmove`), dispatching synthetic `TouchEvent`s the way the Playwright guide's own pinch example does **would not drive TrackballControls at all** — the guide's example is written for apps that listen on touch events directly, which jive-wiki's controls library does not.
3. The one approach that *would* reach real pointer events for two independent touch points — sending raw `Input.dispatchTouchEvent` with two `touchPoints` over a `CDPSession` — is Chromium-only (confirmed both by Question 2's `crInput.ts` reading and by the blog source above, which states plainly *"the Chrome DevTools Protocol is browser dependent and can not be used for testing Firefox"*, and by extension WebKit). This happens to align with jive-wiki's CI, which currently only runs a `chromium` project, but it means dropping below Playwright's public, documented API into an unsupported, Chromium-specific escape hatch (`page.context().newCDPSession(page)` + raw protocol calls) to get a *realistic* two-pointer gesture.

**Answer to "is this realistically testable in CI": not with Playwright's supported public API, no.** A genuine multi-touch pinch/rotate test against real `TrackballControls` pointer-capture logic would require either (a) untrusted synthetic `PointerEvent` dispatch via `page.evaluate()` — reaching the right event type, but not trusted, and needs to be built and validated by hand rather than using Playwright's documented touch guide as-is — or (b) raw CDP `Input.dispatchTouchEvent` calls with two touch points, which is undocumented-for-this-purpose, Chromium-only, and per the blog source's experience with the related `synthesizePinchGesture` command, has a track record of CI flakiness even when it does work. Given jive-wiki's own prior conclusion in the WebGL testing research (issue #6) that flaky, environment-sensitive test strategies aren't worth the CI cost for this project, and that the mobile map's own "Out of scope" section already excludes deep mobile-specific engineering effort, **multi-touch gesture testing should be left to manual verification** rather than built into the automated suite; a single-tap node-click and tap-outside-to-close, per Question 2, remain realistically automatable and should be the actual CI addition.

Sources: [`TrackballControls.js` (raw, `mrdoob/three.js` `dev`)](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/controls/TrackballControls.js), [`three-render-objects.js` (raw, default `controlType`)](https://raw.githubusercontent.com/vasturiano/three-render-objects/master/src/three-render-objects.js), [microsoft/playwright#2903](https://github.com/microsoft/playwright/issues/2903), [microsoft/playwright#39043](https://github.com/microsoft/playwright/issues/39043), [Playwright docs: Touch events (legacy)](https://playwright.dev/docs/touch-events), [Martin Grandrath, "Testing touch gestures with Playwright"](https://www.martin-grandrath.de/blog/2024-05-01_testing-touch-gestures-with-playwright.html).

## Recommendation

1. **Add a second Playwright project using `devices['Pixel 5']` (or `Pixel 7`/`Pixel 8`)**, not an iPhone profile — it's `defaultBrowserType: 'chromium'`, so it runs on the browser binary already installed in CI (`npx playwright install --with-deps chromium`), and its `viewport` (393×727 / 412×839) sits squarely in the ~360–430px phone-portrait target. Only reach for an `iPhone *` profile (WebKit) later, deliberately, if Safari-specific behavior becomes a concern — that's an explicit `playwright install --with-deps webkit` addition to `ci.yml`, not a drop-in.
2. **Reuse the existing `graph2ScreenCoords()` + computed-point interaction pattern, swapped to `page.touchscreen.tap(x, y)`** instead of `page.mouse.move/down/up`, for the "tap a node → panel opens" and "tap outside → panel closes" cases — `3d-force-graph`'s click handling is Pointer-Events-based, and `touchscreen.tap()` is Playwright's real (protocol-dispatched, trusted) single-touch primitive, making it the direct touch analogue of the current `realClick()` helper. Verify empirically whether the existing pre-press "settle a frame after `pointermove`" logic is still needed before a bare `tap()` (it has no explicit `pointermove` phase) — this is the one open empirical question from Question 2's gotchas, worth a quick spike before writing the full spec.
3. **A ~375px-wide layout-overflow check is a plain layout assertion** (e.g. asserting `document.documentElement.scrollWidth <= viewport width` or checking the detail panel's bounding box stays within the viewport) — no touch/canvas interaction needed, trivially portable to the mobile project once it exists.
4. **Do not attempt automated pinch/rotate (multi-touch) coverage.** Playwright has no supported multi-touch API (confirmed still-open as of Jan 2026 per #39043), the one documented workaround (synthetic `TouchEvent` dispatch) doesn't reach jive-wiki's actual `TrackballControls` code path (which listens on `PointerEvent`s, not `TouchEvent`s), and the only approach that would reach it — raw two-point CDP `Input.dispatchTouchEvent` — is unsupported-for-this-purpose, Chromium-only, and has an independently-reported flakiness history. This is consistent with the mobile map's own scoping (no dedicated mobile-performance/gesture engineering) and the project's established preference (from issue #6) for deterministic, non-flaky test strategies over ones that chase full interaction fidelity. Leave pinch/rotate to manual verification on a real device.
